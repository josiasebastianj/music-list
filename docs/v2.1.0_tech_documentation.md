# setlist.app v2.1.0 — Technical Documentation

## 1. Release Information

- **Application:** setlist.app
- **Version:** 2.1.0
- **Author:** josiasebastianj
- **Release type:** Visual redesign / UX restructuring
- **Baseline:** v2.0.0
- **Runtime:** Client-side HTML/CSS/JavaScript
- **Persistence:** Browser `localStorage`
- **External backend:** None

---

## 2. Architecture

The application is a single self-contained HTML document containing:

- HTML structure
- CSS design system
- JavaScript application state and behavior

The application follows a lightweight client-side architecture:

```text
HTML
├── App Header
├── Event / Song Workspace
├── App Footer
└── JavaScript Application
    ├── State
    ├── Normalization / Migration
    ├── Persistence
    ├── Rendering
    ├── Event actions
    ├── Song actions
    ├── Song Detail actions
    ├── Theme management
    └── PNG / JSON export
```

No server or database is required.

---

## 3. Data Model

The canonical persisted model is:

```js
{
  eventName: "",
  eventDate: "",
  songs: [
    {
      id: "...",
      title: "",
      baseKey: "",
      sections: [
        {
          id: "...",
          name: "",
          color: "#8fc5ff",
          note: ""
        }
      ]
    }
  ]
}
```

### Event

```js
{
  eventName,
  eventDate,
  songs
}
```

### Song

```js
{
  id,
  title,
  baseKey,
  sections
}
```

### Song Detail

The application uses the property name `sections` internally, while the UI calls these items **Song Details**:

```js
{
  id,
  name,
  color,
  note
}
```

The `note` belongs to the individual Song Detail. There is no Song-level `note` field.

---

## 4. State and Persistence

### Event data

Event data is persisted under:

```text
setlistApp_v2_0_0
```

The storage key remains compatible with the v2 data model even though the application release is now v2.1.0.

### Theme data

Theme preference is stored separately under:

```text
setlistApp_theme
```

Supported values:

```text
light
dark
```

Theme preference is UI state and is not included in Event JSON data.

---

## 5. Normalization and Migration

Incoming state is passed through normalization before being used.

Key normalization functions:

- `normalizeSections()`
- `normalizeSong()`
- `normalizeEvent()`

Normalization provides:

- Stable IDs when missing
- String validation for title/key/name/note fields
- Section color validation
- Safe fallback colors
- Consistent array structure

### Legacy single-song migration

Older data using:

```text
Song
└── sections
```

can be converted to:

```text
Event
└── songs[]
    └── Song
        └── sections[]
```

Legacy localStorage keys from earlier versions are also checked when the current storage key does not contain usable data.

---

## 6. Rendering Architecture

The UI is rendered from the current state.

Primary rendering functions:

- `render()`
- `renderMain()`
- `renderDetail()`
- `renderSidebarOnly()`

### Navigation

`activeSongId` identifies the Song currently displayed in the main workspace.

The sidebar renders all Songs.

The main workspace renders only the active Song.

This creates the architecture:

```text
Sidebar
  ↓ select
activeSongId
  ↓
Main Workspace
```

## 7. Event Operations

Supported Event operations:

- Edit Event Name
- Edit Event Date
- Reset Event
- Export JSON
- Import JSON
- Switch Light/Dark Theme

### Reset

Reset creates the blank state:

```js
{
  eventName: "",
  eventDate: "",
  songs: []
}
```

A confirmation is required.

If persistence fails, the previous state is restored.

## 8. Song Operations

Supported operations:

- Add Song
- Select Song
- Edit Song Title
- Edit Base Key
- Move Song Up
- Move Song Down
- Delete Song
- Export Song PNG

### Add Song

Creates:

```js
{
  id: "...",
  title: "",
  baseKey: "",
  sections: []
}
```

The new Song becomes active immediately.

### Delete Song

Deleting a Song also deletes all Song Details owned by that Song.

Confirmation is required.

If persistence fails during reorder/delete operations, the previous state is restored.

---

## 9. Song Detail Operations

Supported operations:

- Add
- Edit name
- Edit note
- Change color
- Move up
- Move down
- Delete

### Add Song Detail

Creates a blank detail:

```js
{
  id: "...",
  name: "",
  color: colors[index % colors.length],
  note: ""
}
```

There is no single `DEFAULT_SECTION_COLOR` constant. New Song Details are assigned the
next color from the `colors` palette array, cycling by position (`index % colors.length`).

There is no default Song Detail when a Song is created.

### Color

Section colors are validated as six-digit hexadecimal colors.

Invalid colors fall back to the default palette.

## 10. JSON Export

JSON export is Event-level.

One JSON file contains:

```text
Event
├── Event Name
├── Event Date
└── All Songs
    └── All Song Details
```

The file is generated client-side and downloaded as:

```text
setlist-event.json
```

---

## 11. JSON Import

JSON import:

1. Reads the selected file.
2. Parses JSON.
3. Normalizes the imported state.
4. Persists the normalized state.
5. Selects the first Song, if available.
6. Re-renders the application.

Invalid or unsupported JSON produces an error message.

The file input is reset after the operation so the same file can be selected again.

---

## 12. PNG Export

PNG export is Song-level.

One exported PNG represents one active/selected Song.

The export contains:

- `setlist.app`
- Event Name
- Event Date
- Song Title
- Base Key
- Song Details
- Section colors
- Section notes
- Author
- Version

### Theme-aware export

PNG generation checks the current UI theme.

```text
Light UI → Light PNG
Dark UI  → Dark PNG
```

The export uses a canvas generated in the browser.

### Layout safeguards

The PNG height is calculated from:

- Song title line count
- Song Detail name line count
- Song Detail note line count
- Section spacing
- Footer height

This prevents long notes from being clipped.

### Filename

The Song Title is sanitized before being used as the PNG filename.

## 13. Theme System

Two themes are supported:


```html

```

The theme toggle is intentionally outside the Actions dropdown.

## 15. Responsive Behavior

At mobile widths:

- Header remains on one row where possible.
- Brand tagline is hidden.
- Action controls become compact.
- Sidebar moves above the main workspace.
- Songs are displayed in a compact grid.
- Main Song controls wrap when necessary.
- Song Details use a two-line responsive layout.
- Footer metadata stacks vertically.

---

## 16. Security / Safety Considerations

User-entered text is escaped before being inserted into HTML where required.

Colors are validated before being used in UI rendering.

Imported JSON is normalized rather than inserted directly into the DOM.

No external server is required for Event data.

---

## 17. Known Implementation Notes

The localStorage key intentionally remains `setlistApp_v2_0_0` for continuity with the v2 data model.

The internal `sections` property remains the data-model name for what the UI calls Song Details.

The UI does not persist an active Song selection; on load, the first Song is selected when Songs exist.

Theme preference is persisted independently.
